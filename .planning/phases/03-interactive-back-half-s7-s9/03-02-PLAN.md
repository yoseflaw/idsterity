## Phase Goal

**As a** site visitor who has just absorbed the deficit and institutions narrative, **I want to** click any word in the S8 word cloud and immediately see the top procurement packages containing that word — without waiting for a server — **so that** I can investigate the procurement records behind each keyword on a static site that loads from any CDN.

(Plan 02 delivers the static-data foundation for that vertical slice. The S8 cloud UI and S9 overlay UI are wired in Plan 03 — but the data layer required for instant on-click reveal must exist first.)

<objective>
Extend `dashboard/scripts/prepare-data.py` so a single `uv run` pass emits ~60 new per-word/per-filter JSON files (`dashboard/public/data/word-{word}-{filter}.json`). These files back the SEC-09 record-table overlay: when a user clicks a word in the S8 cloud, the overlay fetches `word-{selectedWord}-{activeFilter}.json` and renders the top 20 inappropriate procurement packages containing that word for that ownership tier.

Purpose: SEC-09 — make the record-table feature feasible on a fully static deploy. There is no server, so all (word, filter) combinations must be pre-baked. The CONTEXT.md decision D-10 locks the naming pattern and shape; this plan implements the bake.

Output: ~60 small JSON files committed alongside the existing `lembaga-totals.json` / `summary-stats.json` outputs, and an extension to `prepare-data.py` that regenerates them on every pipeline run.

This plan is parallel-safe with Plan 01: no file overlap.
</objective>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| inaproc-ds/outputs/ (untrusted-ish) → prepare-data.py | Raw shards are public-source procurement records; values are not user-supplied but may contain malformed data |
| prepare-data.py → public/data/word-*.json (committed) | Outputs are reviewed in PR before commit; baked at build time, not at runtime |
| public/data/word-*.json → browser fetch (Plan 03) | Static files served as `application/json`; consumed by `safeFetch` and rendered via Svelte text interpolation (HTML-escaped) |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-03-06 | Tampering | Malicious string in `paket` or `inappropriateReason` (e.g. `<script>` tag) | mitigate | Output is read by Svelte `{cell}` interpolation in Plan 03, which HTML-escapes by default. No `{@html ...}` used. Plus, source records come from official Indonesian procurement system and are reviewed at commit. |
| T-03-07 | Information Disclosure | Including PII in record fields | accept | The 5 emitted fields are public procurement metadata (institution, work unit, budget, package name, AI reason). No personal identifiers. The raw shards may contain richer fields but only these five are emitted. |
| T-03-08 | Denial of Service (pipeline) | Adversarial paket strings causing pathological substring matches | mitigate | Substring matching `word in paket.lower()` is O(len(paket)) per word per record — bounded. The full pipeline runs offline; runtime is minutes, not real-time. No DoS surface in the browser. |
| T-03-09 | Repudiation | Misleading values committed without provenance | mitigate | Files are produced deterministically from `inaproc-ds/outputs/` shards. The pipeline script is committed and reviewable. Output values are reproducible by anyone with the dataset. |
| T-03-10 | Tampering | Substring match producing false-positive records (e.g. word="sub" matching "subsidi") | accept | Per RESEARCH.md Open Question #2 recommendation and word-cloud.py consistency. Plan 03 will display the record's `paket` text, so users see the actual match context and can judge relevance. |
