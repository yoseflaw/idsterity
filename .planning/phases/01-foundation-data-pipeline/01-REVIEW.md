## Critical Issues

### CR-01: `constants.json` fetch will crash the page silently on any environment where the file does not yet exist

**File:** `dashboard/src/App.svelte:16-23`

**Issue:** `onMount` runs three fetches in a `Promise.all`. `constants.json` is fetched but is not produced by either Python script (`prepare-data.py` or `word-cloud.py`). The file exists in the current repo state as a committed static file, but it is not listed in CLAUDE.md's data-layer documentation and is not regenerated by `npm run prepare-data`. Any fresh checkout that runs `npm run prepare-data` and then serves the site will get a 404 on `/data/constants.json`. Because no `.catch()` exists, the entire `Promise.all` rejects, the `onMount` body exits, and `stats`, `lembaga`, and `constants` are never set — the page shows the loading-pulse state permanently with no user-visible error.

**Fix:** Either (a) generate `constants.json` from the Python pipeline and document it, or (b) remove the fetch if the file is not needed yet and add it back in the phase where it is needed. At minimum, add per-fetch error handling so a missing file doesn't block the whole page:

```js
onMount(async () => {
  try {
    const [s, d, c] = await Promise.all([
      fetch('/data/summary-stats.json').then(r => { if (!r.ok) throw new Error(r.statusText); return r.json(); }),
      fetch('/data/lembaga-totals.json').then(r => { if (!r.ok) throw new Error(r.statusText); return r.json(); }),
      fetch('/data/constants.json').then(r => { if (!r.ok) throw new Error(r.statusText); return r.json(); }),
    ])
    stats     = s
    lembaga   = d
    constants = c
  } catch (err) {
    console.error('Data fetch failed:', err)
    // surface a user-visible error state here
  }
  // ...scroller setup...
})
```

### CR-02: `fetch()` responses are not checked for HTTP errors — a 404 or 500 is decoded as JSON and throws an opaque parse error

**File:** `dashboard/src/App.svelte:16-24`

**Issue:** `fetch(url).then(r => r.json())` does not check `r.ok`. A server returning HTTP 404 (CDN misconfiguration, wrong base path, stale deploy) causes `.json()` to throw because the 404 HTML body is not valid JSON. The error is unhandled (no `.catch()` on the `Promise.all`), so the app silently stalls in loading state. This is distinct from CR-01 but compounds it: even for the two committed files, any hosting misconfiguration becomes invisible to the user.

**Fix:** Check `r.ok` before calling `.json()` on every fetch (shown in CR-01 fix above). This is the standard pattern:

```js
const safeFetch = url =>
  fetch(url).then(r => {
    if (!r.ok) throw new Error(`${r.status} ${r.statusText} — ${url}`)
    return r.json()
  })
```

### CR-03: `label_pagu["unflagged"]` can go negative — corrupting `summary-stats.json`

**File:** `dashboard/scripts/prepare-data.py:67`

**Issue:** `label_pagu["unflagged"] = total_pagu - sum(label_pagu.values())` subtracts the sum of `{"low", "med", "high"}` from `total_pagu`. However, `total_pagu` is accumulated from `*.jsonl` shards (line 30), while `label_pagu` values come from `*_priority.json` shards (line 57-65). If the same record appears in both (which is the expected design — priority files are a subset of the JSONL), this is correct. But if a priority record has a `pagu` value that is not present in any JSONL shard (e.g., because a shard failed to process, or the priority JSONs and JSONL files are from different pipeline runs), `sum(label_pagu.values())` can exceed `total_pagu`, producing a negative `unflagged` value. This corrupts the `summary-stats.json` output without any warning or error.

The same arithmetic risk applies to `label_counts["unflagged"]` on line 68.

**Fix:** Add a guard and emit a warning:

```python
unflagged_pagu   = total_pagu   - sum(label_pagu.values())
unflagged_counts = total_records - sum(label_counts.values())

if unflagged_pagu < 0:
    print(f"WARNING: unflagged_pagu is negative ({unflagged_pagu}); check shard consistency")
if unflagged_counts < 0:
    print(f"WARNING: unflagged_counts is negative ({unflagged_counts}); check shard consistency")

label_pagu["unflagged"]   = max(unflagged_pagu, 0)
label_counts["unflagged"] = max(unflagged_counts, 0)
```

### WR-01: `prepare-data.py` opens JSONL files without explicit encoding — may fail on non-UTF-8 locales

**File:** `dashboard/scripts/prepare-data.py:24`

**Issue:** `path.open()` uses the system default encoding. On Windows (common locale: cp1252) or any system where `LANG` is not set, non-ASCII characters in Indonesian procurement text (e.g., institution names with accented characters) will raise `UnicodeDecodeError`, aborting the entire pipeline.

**Fix:**
```python
for line in path.open(encoding='utf-8'):
```
Apply to both `path.open()` calls at lines 24 and 47, and likewise in `word-cloud.py` at line 52.

### WR-03: `scrollama` scroller is set up inside `requestAnimationFrame` but `onDestroy` may run before the RAF callback fires

**File:** `dashboard/src/App.svelte:25-37`

**Issue:** The `scroller` variable is assigned inside a `requestAnimationFrame` callback. If the component is destroyed before the next animation frame (e.g., in tests, SSR, or rapid navigation), `scroller` will be `undefined` when `onDestroy` runs. The optional chaining `scroller?.destroy()` handles the null case, but `window.removeEventListener('resize', onResize)` is always called regardless. If `scroller` was never initialized, `onResize` was also never registered, so `removeEventListener` is a no-op — this is harmless but the pattern is fragile. A more concrete risk: if `scroller.setup()` throws (e.g., no `[data-step]` elements found in a stub-only layout), the `window.addEventListener('resize', onResize)` call on line 30 is never reached, yet `onDestroy` still calls `removeEventListener` for a listener that was never added. This is safe today but becomes a bug if the RAF callback is refactored.

**Fix:** Track registration explicitly:

```js
let resizeRegistered = false
requestAnimationFrame(() => {
  scroller = scrollama()
  scroller
    .setup({ step: '[data-step]', offset: 0.5, progress: false })
    .onStepEnter(({ index }) => { activeStep = index })
  window.addEventListener('resize', onResize)
  resizeRegistered = true
})

onDestroy(() => {
  scroller?.destroy()
  if (resizeRegistered) window.removeEventListener('resize', onResize)
})
```

### WR-04: `pagu` field treated as integer but `or 0` silently masks non-numeric values

**File:** `dashboard/scripts/prepare-data.py:27`, `dashboard/scripts/word-cloud.py` (not used there)

**Issue:** `pagu = r.get("pagu") or 0` returns `0` for `None`, missing key, empty string, and `False` — but also returns `0` for any falsy non-numeric value (e.g., `""`). If a record has `"pagu": "N/A"` or `"pagu": null`, the `or 0` guard handles it. However if `pagu` contains a string like `"150000000"`, Python will silently use the truthy string and then `totals[name] += pagu` will raise `TypeError: unsupported operand type(s) for +=: 'int' and 'str'` — aborting the pipeline. The guard does not coerce the type.

**Fix:**
```python
pagu = int(r.get("pagu") or 0)
```

### WR-05: `main.js` missing `Source Serif 4` weight variants — body text will fall back to system serif

**File:** `dashboard/src/main.js:4`

**Issue:** `main.js` imports only `@fontsource/source-serif-4/400.css`. CLAUDE.md specifies weights 300 and 600 for Source Serif 4, and the CSS in `App.svelte` references `font-weight: 700` for `Libre Baskerville` (imported correctly) but `Source Serif 4` at 300 or 600 weight is used in body text. The `@fontsource` package requires explicit per-weight imports; the missing weights will cause the browser to synthesize bold/light variants (faux-bold, faux-light), degrading typographic fidelity. Additionally, `@fontsource/source-serif-4` does not handle optical sizing automatically — the CLAUDE.md spec (8–60pt) requires the variable font variant, not the static 400-only import.

**Fix:**
```js
import '@fontsource/source-serif-4/300.css';
import '@fontsource/source-serif-4/400.css';
import '@fontsource/source-serif-4/600.css';
// For optical sizing support, use the variable font package instead:
// import '@fontsource-variable/source-serif-4';
```

### IN-03: `word-cloud.py` does not write `wordcloud-lembaga.json` atomically — partial writes on disk-full or interrupt leave corrupt file

**File:** `dashboard/scripts/word-cloud.py:92`

**Issue:** `Path.write_text()` is not atomic. If the process is killed mid-write (disk full, SIGKILL), the output JSON file is left in a truncated/corrupt state with no indication other than a parse error at runtime. This is a low-probability risk for a developer script but worth noting given that `wordcloud-lembaga.json` aggregates all institutions and could be large.

**Fix:** Write to a `.tmp` file and rename (atomic on POSIX):

```python
import os, tempfile
def atomic_write(path: pathlib.Path, content: str):
    tmp = path.with_suffix('.tmp')
    tmp.write_text(content, encoding='utf-8')
    os.replace(tmp, path)
```
